Regras globais da spec que valem em todas as fases: teto absoluto de abertura 120 min compilado; fail-safe local sempre; payload ≤ ~200 bytes; versão de protocolo em toda mensagem; mismatch = rejeição segura.

Referencia de UI (Fase 5): mockup do painel/portal em `myfork/Irrigacao Mobile.dc.html` (design doc HTML, 2026-07-11) - base visual das telas do painel web e captive portal.

Requisito reforçado pelo usuário (2026-07-11) — modo híbrido/espelho (§5.2 `fonte`): o sistema deve poder operar SOMENTE espelhando as entradas físicas de um controlador externo (réplica das saídas 24VAC lidas por optoacoplador), sem cronograma próprio. Isso deve ser configurável por entrada, incluindo a polaridade do estado ativo (active-high / active-low). Entra na Fase 4 (gateway/zonas) e no pin map da Fase 2 (campo de polaridade por entrada física).

Requisito reforçado pelo usuário (2026-07-12) — modo espelhamento (§5.2 `fonte`, Fase 4): quando ativo, TODA configuração e TODOS os intertravamentos são bypassados — a estação escrava replica cegamente o estado da entrada do mestre. O bypass é configurável pela UI; a UI também permite associar cada entrada do mestre (gateway híbrido, opto 24VAC) a qualquer saída de qualquer escravo (mapeamento entrada→(nó,saída) via dropdown). Polaridade ativo-alto/baixo por entrada (requisito 2026-07-11) continua valendo. Nota de engenharia: o teto fail-safe de 120 min compilado (§4.2) permanece mesmo em espelhamento, salvo decisão explícita do usuário em contrário — a renovação periódica do comando cobre acionamentos longos.

Requisito do usuário (2026-07-12) — exportar chave da fazenda: função de visualizar a PSK do canal primário (base64 + nome do canal) para cadastro no cofre do device de serviço (§11.2). Fase 3: pressão longa no botão do gateway despeja no console serial. Fase 5: mesma função exposta no painel web (com PIN).

Feature adicional (2026-07-30) — **controle de nível por boia (enchimento automático)**: uma boia (sensor digital) num nó controla a partida/parada de um motor/bomba (uma zona) em outro nó ou no GPO do gateway. Aditiva pós-Fase 8 (spec `2026-07-30-irrigacao-controle-nivel-boia-design.md`, plano `2026-07-30-irrigacao-controle-nivel-boia.md`). Nova peça = ação **positiva** (liga quando nível baixo) que o intertravamento — só negativo (bloquear/fechar) — não fazia. Abordagem A: `LevelControlTable` (config + persistência LittleFS própria `irrigation_niveis.dat`) + `LevelControlEngine` puro (máquina start/stop/renew/stale, histerese por tempo minOn/minOff, 1 boia) no gateway, dirigindo o `routeZoneToGroup`/`gwDriveZone` existente (herda sequência de bomba, veto de intertravamento, `max_partidas_hora`). Fail-safe: boia muda > `staleTimeoutS` → desliga + alerta `NIVEL_BOIA_MUDA`; teto 120 min sempre corta; RENEW (60 s) mantém vivo só enquanto quer-encher **e** boia fresca. Codec web + endpoints CI-only `/api/irrigation/levels[/delete]` + aba "Nível" no painel; regras no backup §5.5 (`niveisJson`). Aditivo total: protocolo VERSION=1, ABI settings v5 (176 B) intactos, sem novo tipo de wire; enums append-only `AuditOrigin::NIVEL`/`AlertType::NIVEL_BOIA_MUDA`. 2 suites nativas novas (`test_level_control_table`/`test_level_control`), `native-suite-count` 62→64. **Banca 2+ nós exigida antes de campo** (boia-nó→gateway→bomba-nó, frescor real e endpoints CI/banca-only não são native-testáveis). Fora de escopo (YAGNI): 2 boias / sensor analógico com 2 limiares, modo esvaziar/drenar, controle local sem gateway, cifra PSK. Follow-ups em `.superpowers/sdd/progress.md`.

Feature adicional (2026-08-08) — **Modo Remoto (botoeira → saída remota + LED)**: uma botoeira (botão momentâneo numa entrada digital) no gateway **ou** em qualquer nó aciona (toggle-latch) uma saída em outro nó/gateway; múltiplas botoeiras em múltiplos nós podem controlar a mesma saída; LEDs dedicados dão feedback no nó da botoeira (pisca ao transmitir → fixo ao confirmar → apaga em falha, **e** acende sempre que a saída está ativa por qualquer origem — estado compartilhado). Spec `2026-08-08-irrigacao-modo-remoto-design.md`, plano `2026-08-08-irrigacao-modo-remoto.md` (11 tasks, subagent-driven). Arquitetura **gateway-central**: associações em `RemoteButtonTable` (flash própria `irrigation-remote.dat`, editada no painel); estação detecta borda+debounce (`RemoteButtonEdge`) → **`MSG_REMOTE_TRIGGER`** (14) → gateway resolve o toggle lendo o estado REAL do atuador (`gwZoneIsOpen`: driver local `valves.isOpen`/`gpos.isOn` / `StationTelemetry.valveStates|gpoStates` / grupo) e aciona via `gwSendValveCmd` (herda fail-safe/intertravamento/grupo/local+remoto); gateway empurra **`MSG_REMOTE_LED`** (15) change-driven → `RemoteLedFsm` no nó (todos os papéis dirigem `pinsRemoteLed[2]`). Botoeira local do gateway roda em processo. **ABI settings v6→v7** (append-only 180→184: `pinsRemoteLed[2]`+`digitalInBtnMask`+`digitalInLedIdx`; `StationEntry.blob` 180→184, `STATION_ENTRY` 215→219). Protocolo VERSION=1 (msgs 14/15 aditivas). Config de botão/LED por estação é derivada das associações e empurrada via `SET_CONFIG` (§5.4); self-node grava nos settings do próprio gateway. Auth = anti-replay+`senderAuthorizedBy` no TRIGGER (fire-and-forget, sem ACK); REMOTE_LED idempotente filtrado por `boundGateway`. Backup §5.5 inclui `remoteButtons`. Endpoints CI-only `/api/irrigation/remote[/delete|/command]` + aba "Modo Remoto" em "Mais" (dedup por saída no card de teste, LED por gatilho, sem pill global — fiel ao mockup `Irrigacao Mobile.dc.html` com esses refinamentos). 2 suites nativas novas (`test_remote_button_table`/`test_remote_button`), `native-suite-count` 69→71; **suíte completa 1024/1024 GREEN + build nativo SUCCESS** (Docker). **Banca 2+ nós EXIGIDA antes de campo** (trigger/LED/toggle por rádio + shared-state não são native-testáveis) + **build ESP32 no CI** (endpoints webserver-guarded + pinos de LED no variant).
